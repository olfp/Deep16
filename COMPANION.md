# A companion board for the D16nano: USB keyboard and sound

Status: **design note, nothing implemented.** The 9K tile build measured
**4,237 / 4,320 CLS with 83 CLS free** on 28 Oct 2026 (`SLIMPLAN.md` §1), after
the segmented PSRAM map, the SD card and the user-flash read port landed. The
two features the machine is missing — a USB keyboard and sound — do not fit in
83 CLS: the USB core alone is ~160, and the sound engine is another 300-360
LUT4. This note fixes where they go instead, how they attach without touching
the 9K's fabric, and what the companion contains. Companion area figures are
±40 % until the companion is synthesised.

Companions: `SLIMPLAN.md` (the 9K's area budget), `AUDIOPLAN.md` (the on-die
audio design this replaces), `HARDWARE.md` (PS/2, SPI, the USB core
reference), `doc/Interrupts.md` (the interrupt model).

## 0. The recommendation, in one paragraph

A second small Gowin board (**Tang Nano 4K** preferred, 1K possible) carries
everything new: it is a **USB HID host that presents itself as a PS/2
keyboard** to the existing, untouched `rtl/ps2_rx.sv`, and a **4-voice
sound engine** (NES APU class) fed over the 9K's existing SPI master through
**one new chip select**. The 9K gains no RTL except a third bit on
`cs_n` (~1-2 CLS, one pin) and a handful of Forth words. If the companion is
absent, the physical PS/2 keyboard still works and the machine is exactly what
it is today.

## 1. Why a companion, and what it is not

`HARDWARE.md:83-103` already names the right USB core: nand2mario's
`usb_hid_host`, **<300 LUTs, <250 registers, 1 BRAM**, no CPU, no PHY, and it
is a *low-speed (1.5 Mbit/s) host driven by a single 12 MHz clock*. That is
roughly five times smaller than the full-speed host I assumed earlier, and it
removes the "USB needs an MCU" argument entirely.

It is still ~160 CLS plus a 12 MHz clock domain, a scancode path and a
keyboard FIFO writer — twice the 83 CLS the 9K has free, and the sound engine
is another 300-360 LUT4. Neither fits, so the question is not *whether* to add a board but
*what the board must do* and *how little the 9K can be asked to change*.

What it is not:

- not a second D16. The companion has no CPU, no memory map and no code that
  the emulator must model beyond a register interface;
- not a replacement for the 20K. The 20K (20,736 LUT4, 4 PLLs, 46 BSRAM) can
  hold USB and the full sound chip on one die; this note records where that
  fork sits (§10) rather than pretending the 9K can grow.

## 2. The attachment: two variants

### 2.1 Variant A — the companion emulates a PS/2 keyboard (recommended)

The 9K's `rtl/ps2_rx.sv` is untouched. The companion drives the PS/2 pair
(pins 76/77) as an open-drain keyboard: start bit, 8 data bits LSB first, odd
parity, stop bit, 11 bits at 16.667 kHz (12 MHz / 720), 660 µs per frame.

What the 9K sees is a keyboard. Nothing else changes: the Set-2 decoder, the
modifier tracking, the `2048 × 8` BSRAM pROM (`ps2map.hex`, generated by
`scripts/make_ps2map.mjs`), the keyboard FIFO and the console path all run as
they do today.

| | Value |
|---|---|
| 9K RTL | **none** |
| 9K CLS | **0** |
| 9K pins | the two PS/2 pins stay in use |
| 9K software | none for keys |
| Tests | `scripts/build_ps2_sim.sh` already covers the 9K side |
| Companion absent | the physical keyboard still works |
| E0 / arrows | still ignored (`ps2_rx.sv:17-19`) |

The cost lands on the companion: a PS/2 device transmitter with parity and a
clock divider, plus a 12 MHz domain that is asynchronous to the 9K. Neither is
hard; both are ~90 LUT4.

### 2.2 Variant B — scan codes over SPI

Delete only the PS/2 *sampler* (synchronisers, edge detect, 11-bit shift,
parity, timeout; ~60-90 LUT4), keep the decoder and the pROM, and add an
**injection port**: one MMIO byte write that presents a byte to the decoder
with a `valid` pulse (~10 LUT4). The companion sends bytes in PS/2 Set-2 wire
format (`E0`, `F0`, code) over SPI and the 9K injects them.

| | Value |
|---|---|
| 9K RTL | injection port, sampler deleted |
| 9K CLS | **-15 to -25** (`u_ps2` is 95 LUT in total, decoder included) |
| 9K pins | 76/77 freed |
| 9K software | one non-blocking poll in the console input path |
| Tests | new byte-vector path, but it shares the decoder's vectors |
| Companion absent | **no keyboard** |
| Companion cost | ~90 LUT4 less than variant A (no PS/2 transmitter) |

Variant B is the one that *gives area back*, and it is the better testing
story: the same byte vectors drive the RTL port, the JS/WASM keyboard input and
the companion's translator, so "USB and PS/2 behave identically" becomes a
suite instead of a claim. It also opens the door to fixing extended keys in one
place — which is worth doing whenever `ps2_rx.sv` is next touched, because
arrows and nav keys do not work today on either path.

### 2.3 Which one

| | Variant A (PS/2) | Variant B (scan codes) |
|---|---|---|
| 9K risk | none | small, but it is RTL |
| 9K CLS | 0 | -15 to -25 |
| Companion LUT4 | 870-940 (76-82 %) | 780-850 (68-74 %) |
| Companion pins | 2 PS/2 + 4 SPI + 2 USB + 1 audio | same, 2 PS/2 pins freed |

**Variant A if the companion is a 4K; variant B if it must be a 1K.** Variant A
is the one to build first because it cannot break the machine that already
works, and variant B can follow later without changing the companion's USB
side: only the transport between the companion and the 9K changes.

## 3. The sound link, and the chip select

### 3.1 Why a chip select

`rtl/deep16_spi.sv` is an 8-bit master with two chip selects, `cs_n[0]` = SD
(pin 38) and `cs_n[1]` = external flash (pin 25), and **both are active while
the machine runs** — the build has the external flash as a live store and the
SD card as a live filesystem (`d16: segmented PSRAM map, SD card, source from
the card`). There is no free select.

Three ways to attach a third device:

| Option | 9K cost | Verdict |
|---|---|---|
| Magic-word sniffing (no CS) | 0 pins, 0 CLS | works, but the companion drives MISO on a bus the storage is using, and a tri-state bug corrupts a filesystem silently |
| **Widen `cs_n` to 3 bits** | **1 pin, ~1-2 CLS** | **recommended** |
| Decode `cs_sel == 2'b11` as "companion" | 1 pin, ~1 LUT | works only because nothing writes `11` today; an undocumented overload |

Take the chip select. It is the cheapest LUT in the design:

- framing becomes **"the bytes between CS edges"** — no magic matcher, no CRC
  for framing, no resynchronisation after SD or flash traffic;
- MISO contention is **impossible by construction**: the companion is
  deselected whenever SD or flash is selected, and vice versa;
- a frame cut short by a reset simply aborts, so the companion cannot wedge;
- the companion saves ~40 LUT4 (the matcher and the MISO timeout);
- the 9K driver is the pattern it already uses: *select, shift bytes,
  deselect*, so one driver serves three devices.

### 3.2 The change to the 9K

```
rtl/deep16_spi.sv     cs_n [1:0]  -> [2:0]
                      cs_sel[1:0] -> [2:0]     (wdata[2:0], rdata zero-extended)
rtl/deep16_top.sv     port width
rtl/deep16_board.sv   port width + one IO_LOC in rtl/deep16_board.cst
```

`u_spi` is 55 LUT today (`SLIMPLAN.md` §3), so the third select is ~1 CLS -
affordable even with 83 free.

`cs_sel = 1` (SD) and `= 2` (flash) keep their meaning, so existing software
and the storage paths are untouched; `= 4` selects the companion. The change is
additive and must land with the SD and flash simulations re-run
(`scripts/build_spi_sim.sh`).

### 3.3 Frames

Fixed four bytes per transaction, so one code path serves read and write:

```
CS low
  byte 0  command   0x01 write, 0x02 read, 0x00 idle
  byte 1  register  0x00-0x3F
  byte 2  high      write: data high   read: returned high (dummy out)
  byte 3  low       write: data low    read: returned low  (dummy out)
CS high
```

Four bytes is 9.5 µs of shift time at 3.375 MHz plus ~40 cycles of per-byte
MMIO overhead, so a register write is ~130 cycles. `SFX n` writing eight
registers is ~1,000 cycles (150 µs), about 1 % of a 60 Hz frame — acceptable,
and a block-write command can halve it later if a game ever notices.

## 4. The sound engine

### 4.1 The feature set to copy: the NES APU

Two pulse channels, one triangle, one noise, 4-bit hardware envelopes, a sweep
unit and length counters ran collision effects, explosions, coins, jumps and
full soundtracks for a decade. That is the minimum that still sounds like a
game, and it is also a *known* feature set with documented register semantics.

### 4.2 A uniform 4-voice version (smaller than the NES-shaped one)

Rather than fixed pulse/pulse/triangle/noise channel types, give all four
voices the same shape:

| Per voice | Contents |
|---|---|
| `PERIOD` | 16-bit phase increment (pitch) |
| `VOL_ENV` | 4-bit volume, 4-bit decay rate |
| `CTRL` | enable, waveform (pulse / triangle / saw / noise), duty, length-halt |
| `SWEEP` | signed 8-bit period delta, 4-bit rate |

- **One shared 15-bit LFSR**, clocked by a voice's own phase MSB. Because the
  noise is clocked by the voice, *noise has pitch*, and the sweep unit works on
  it for free — which is exactly what makes an explosion sweep down.
- **One shared, time-multiplexed sweep adder** (4 voices × 24 kHz = 96 k
  updates/s, 125 cycles per update at 12 MHz — plenty of time).
- **Four 4-bit envelopes** that decrement at the programmed rate; at zero the
  voice stops (or holds, per `CTRL`).
- Mixer: 4 × 4-bit volumes into a 6-bit sum, then a 1-pole tilt at ~6 kHz to
  take the edge off the pulse waves, then a 16-bit first-order sigma-delta.

| Block | LUT4 |
|---|---|
| 4 phase accumulators (16-bit) | 60-70 |
| 4 waveform muxes + duty | 35-45 |
| 15-bit LFSR | 15 |
| 4 envelopes | 30-40 |
| shared sweep adder | 15-20 |
| 4 length counters | 30-40 |
| mixer + tilt | 30-40 |
| sigma-delta | 25-30 |
| rate divider + register decode | 50-60 |
| **subtotal** | **290-360** |

Register file: 24 words × 16 bits = 384 FFs (no LUT cost, written from the SPI
side). No sample memory, no wavetables, no per-voice filter, no stereo.

### 4.3 Register map

| Addr | Name | Function |
|---|---|---|
| `0x00` | ID | read: `{8'hD1, 4'b0, voices}` — also the "companion present" probe |
| `0x01` | CTRL | b0 enable, b1 mute, b2 soft reset |
| `0x02` | VOL | master volume 0-15 (right shift) |
| `0x03` | STATUS | read: voice-active mask, frame error |
| `0x04` | RATE | sample divider, 12 MHz / (RATE+1); 499 = 24 kHz |
| `0x10 + 4n` | PERIOD | voice n pitch |
| `0x11 + 4n` | VOL_ENV | volume / decay rate |
| `0x12 + 4n` | CTRL | enable, waveform, duty, length-halt |
| `0x13 + 4n` | SWEEP | signed delta / rate |

### 4.4 Sample rate

**24 kHz, not 15 kHz.** OSR is 500 at 12 MHz (first-order SNR ~55-60 dB, fine
through a two-pole RC), and the pulse waves' images land at 24 kHz where the
filter kills them — at 15 kHz they alias into the audible band. It costs one
comparator and no CPU.

The analogue side is unchanged from `AUDIOPLAN.md` §5: two RC sections
(1 kΩ / 10 nF each) into 100 Ω and a 10 µF coupling capacitor, silence at
VDD/2, and nothing but a 3.3 V pin on the companion.

## 5. Effects, and where they live

**The effects library lives in Forth, not in the companion.** The hardware is
four channels of registers; allocation is a policy, and policy belongs on the
CPU that has the game state.

`SFX ( n -- )` indexes a table in the dictionary and writes two channels:

| Effect | Layer 1 | Layer 2 |
|---|---|---|
| hit / collision | triangle ~90 Hz, fast decay (40 ms) | noise burst, fast decay (40 ms) |
| crash | noise, downward sweep | triangle thump |
| explosion | noise, slow downward sweep (600 ms) | — |
| laser | pulse, fast downward sweep | — |
| jump | pulse, upward sweep | — |
| coin | pulse, two-note arpeggio (two writes) | — |
| powerup | pulse arpeggio, rising | — |
| gameover | triangle descent | — |

Two layers are why a hit sounds like a hit: the thump gives it weight, the
noise burst gives it edge, and neither alone is convincing. The cost is eight
register writes, ~1,000 cycles, paid by the game loop at the moment of
collision — and nothing else, because the hardware runs the envelope to
completion on its own.

`NOTE ( voice period -- )`, `SFX? ( -- mask )` and `MUTE ( flag -- )` complete
the API. A music player is ordinary Forth.

## 6. Clocking

`usb_hid_host` needs **12.000 MHz**, because its 1 ms timer is hardcoded as
12,000 clocks and 1.5 Mbit/s sampling depends on it.

27 MHz × 4 / 9 = 12.000 MHz exactly, so the companion's single rPLL can do it:
`IDIV_SEL = 8` (divide by 9) and `FBDIV_SEL = 3` (multiply by 4), the same
convention as `rtl/psram/psram_pll.v`. Choose `ODIV` so the VCO stays in the
part's 400-1200 MHz range — 64 puts it at 768 MHz. **Check this against the
GW1NZ/GW1NSR rPLL specification before committing the board.**

Run the **whole companion at 12 MHz**: USB, PS/2 transmitter, APU and
sigma-delta in one domain, no CDC, one PLL. The PS/2 bit period is then an
exact 720 cycles. The 9K's 6.75 MHz domain and the companion's 12 MHz domain
meet only at the asynchronous PS/2 pins and the SPI frame, both of which are
already asynchronous by design.

Note the 9K cannot make 12 MHz: its 27 MHz oscillator divides only to 13.5 / 9
/ 6.75 / 5.4..., and both of its PLLs are committed (PSRAM 51 MHz, DVI
371.25 MHz VCO). That is the concrete reason USB cannot live on the 9K even if
the LUTs existed.

## 7. USB host details

### 7.1 The low-speed caveat

The core is **low-speed only**; its own TODO list says full-speed, hubs and
XBOX360 controllers are future work. In practice:

- plain wired keyboards (the usual membrane or mechanical type): usually
  low-speed, should work;
- RGB/gaming keyboards, wireless dongles, anything behind a hub: full-speed,
  **will not enumerate**.

This must be tested with the actual keyboards before anything else in the plan
depends on it. The physical PS/2 port staying (variant A) is what makes this
safe: a keyboard that does not work on USB still works on PS/2.

### 7.2 HID to Set-2

| Step | Detail |
|---|---|
| scancode table | HID usage -> Set-2 code, 1 BSRAM block + ~20 LUT4 of address glue |
| make / break | key in report and not before -> make; dropped -> `F0` + code |
| modifiers | USB reports a bitmask, not scancodes: the companion **synthesises** the Set-2 modifier make/break codes (`12`, `59`, `14`, `11`) when the bitmask changes, because `ps2_rx` tracks them itself |
| extended | `E0` prefix for arrows/nav — sent, but ignored by the 9K until §2.2's decoder fix |
| auto-repeat | USB keyboards do not repeat; PS/2 keyboards do. The companion must repeat: 500 ms delay, then 30 Hz |

### 7.3 Listen before talk

PS/2 is open-collector, so a physical keyboard and the emulator may share the
pair as a wired-AND — and if both transmit, the host sees garbage. The
companion watches the pair and stays silent while a real keyboard is talking
(~10 LUT4). That turns "use one at a time" into a property of the hardware.

### 7.4 The 2 ms deadline

`ps2_rx` resynchronises after 2 ms without a clock edge
(`TIMEOUT = CLK_HZ/500`) and sets `frame_error`. A frame is 660 µs, so the
PS/2 transmitter must be the companion's highest-priority task — if the APU
and the USB side ever contend, the *sample* tick loses, never the frame.

## 8. Companion budget and part choice

| Block | LUT4 |
|---|---|
| `usb_hid_host` (1 BRAM) | 300 |
| HID -> Set-2 table (1 BSRAM) + make/break + modifiers | 100 |
| auto-repeat | 40 |
| PS/2 transmitter + listen-before-talk (variant A only) | 90 |
| SPI slave with CS | 50 |
| sound engine (§4.2) + tilt + sigma-delta | 290-360 |
| **total, variant A** | **870-940 of 1,152 (76-82 %)** |
| **total, variant B** | **780-850 of 1,152 (68-74 %)** |

At ±40 % these ranges can reach 90 %, which is where the 9K is unhappy today.
So:

| Part | LUT4 | Verdict |
|---|---|---|
| **Tang Nano 1K** (GW1NZ-1) | 1,152 | possible at 76-82 % (worst case ~90 %); placement is the risk, not logic |
| **Tang Nano 4K** (GW1NSR-4C) | 4,608 | comfortable (~20 %), 10 BSRAM, 2 PLLs |
| Two 1Ks | 2 × 1,152 | works, but two bitstreams for one feature set — reject |
| Tang Nano 20K as companion | 20,736 | wasteful: if you are buying one, make it the main board (§10) |

**Recommendation: 4K.** The 1K saves ~$10 and spends the entire safety margin
of both boards.

## 9. The I2C port (reserved, not built)

If variant B is ever taken, pins 76/77 are free and are *already* configured
for I2C's electrical contract: open-drain lines with pull-ups to 3.3 V
(`IO_PORT ... PULL_MODE=UP`). Add `OPENDRAIN=ON` and they are SDA/SCL. With
variant A they stay PS/2, and the same port is available on any two of the 45
free I/O pins instead.

Do not build the master yet. A minimal master-only engine (single byte, no
clock stretching, no arbitration) is 80-120 LUT4 — more than variant B frees -
and a bus with no devices is 40-60 CLS of nothing. Reserve the pins and the
address plan, and pay when a peripheral exists:

| Device | Address | Why a retro machine wants it |
|---|---|---|
| RTC (DS3231 / PCF8563) | 0x68 | timestamps on files, a `TIME` word |
| EEPROM | 0x50 | settings that survive power-off without the flash |
| OLED (SSD1306) | 0x3C | a 128 × 64 status panel with no video-path cost |
| GPIO expander | 0x20 | buttons/joystick without touching fabric |
| ARA (SMBus alert) | 0x0C | how an I2C device raises an interrupt |

"Interrupt" on I2C means **SMBus ALERT#**: one extra open-drain line, and the
host reads 0x0C to find out who is asking. It costs the same pin as an SPI
interrupt and belongs with the port, not with the companion.

## 10. The 20K fork

| | 9K + companion | 20K |
|---|---|---|
| Fabric | 9K at 83 CLS free, companion at 68-82 % | 20,736 LUT4 (2.4x the 9K) |
| USB clock | companion's PLL | 4 PLLs, one free for 12 MHz |
| Boards / bitstreams / flashes | 2 / 2 / 2 | 1 / 1 / 1 |
| Link, protocol, PS/2 | needed | **none** |
| Sound | 4 voices, no samples | 8 voices + sample channel on-die |
| Blocker | none | **64 Mbit SDRAM, not PSRAM** — `rtl/psram/` needs a new controller |

The 20K is the capacity fix; the companion is a capacity workaround that also
happens to be a good sound chip. If the 9K is to stay alive as the cheap
machine — which is the stated goal — both exist, and the APU should be written
portable from day one so it drops into the 20K unchanged when the SDRAM
controller lands.

## 11. Integration and pin plan

| Signal | 9K pin | Direction | Notes |
|---|---|---|---|
| SPI SCK | 36 | out | existing |
| SPI MOSI | 37 | out | existing |
| SPI MISO | 39 | in | existing; companion drives only while selected |
| SPI CS2 (companion) | TBD free J6 | out | **new** (`cs_n[2]`) |
| PS/2 clock / data | 76 / 77 | in | existing, open-drain, pull-ups |

Companion I/O: USB D+ / D- (2 pins, 15 kΩ to GND on each, VBUS 5 V and GND
from the 9K header), PS/2 clock / data (2 pins, open-drain), SPI SCK / MOSI /
MISO / CS (4 pins), audio out (1 pin). Nine I/O plus power.

The companion taps the PS/2 pair on the **3.3 V side of the existing level
shifter**, not at the mini-DIN. Both sides are open-collector, so a physical
keyboard and the emulator can share the pair, but only one may transmit at a
time — which is what §7.3 enforces. Check the shifter type before wiring: a
BSS138-style bidirectional shifter is happy being driven from the 3.3 V side,
a one-way buffer is not.

Boot order and failure: the companion boots from its own flash; the 9K does
not wait for it and must report `D1` from the ID register or "absent". A
companion that is absent or running old firmware must degrade to PS/2-only
keyboard and no sound, never to a hang — hence the fixed 4-byte frames and the
ID probe.

## 12. Test plan

- **Companion testbench, keyboard:** instantiate `rtl/ps2_rx.sv` as the *host*
  in the companion's Verilator testbench. The 9K's real receiver becomes the
  golden model, so the transmitter is tested against the thing it must satisfy.
- **Scan-code vectors (variant B):** one byte-vector file drives the RTL
  injection port, the JS/WASM keyboard input and the companion's translator.
- **Sound, offline:** render 100 Hz, 1 kHz and a sweep at 24 kHz; FFT the
  one-bit stream; assert frequency (±1 %), SNR > 40 dB, that silence is a 50 %
  duty stream, and that envelope decay times match the programmed rate.
- **Effects:** for each preset, assert the pitch trajectory and the decay time
  from the rendered stream, so a "crash" cannot silently become a "blip".
- **SPI:** frame assembly, early-CS abort, register read-back, and a write to
  the companion register space that must not disturb the SD or flash selects.
- **9K regression:** `scripts/build_spi_sim.sh` green after `cs_n[2:0]`, and
  the whole suite green with the third select present and unused.
- **Absent companion:** the 9K boots, the console works over UART, and the
  physical PS/2 keyboard still types.

## 13. Phases

| Phase | Work | Exit criterion |
|---|---|---|
| C0 | `cs_n[2:0]` + one free pin, companion select unused | SD and flash sims green |
| C1 | companion at 12 MHz, SPI slave, register file, ID | ID reads `D1`; frames round-trip |
| C2 | 4-voice engine + sigma-delta + RC | offline tone/SNR/envelope tests pass |
| C3 | PS/2 transmitter + HID->Set-2 + repeat, tested against `ps2_rx` | a synthetic key types in the 9K's sim |
| C4 | `usb_hid_host` + listen-before-talk, real keyboard | keys arrive from a real USB keyboard |
| C5 | Forth `SFX` / `NOTE` / `SFX?` + effect table | collision and crash audible in the demo |
| C6 | optional: scan-code variant B, I2C master + ALERT | as needed |

C3/C4 can run in parallel with C5 once C2 is green: keyboard and sound share
only the SPI slave.

## 14. Risks

| Risk | Mitigation |
|---|---|
| Companion does not place at 76-90 % on a 1K | 4K (§8); the design is the same RTL |
| The 9K's 83 CLS free shrink further | the only 9K change here is `cs_n[2]`, ~1 CLS; nothing else is spent |
| 12 MHz cannot be made from 27 MHz on that part | check the rPLL spec first (§6); fallback is a 12 MHz can oscillator on the companion |
| The keyboard is full-speed and does not enumerate | test the real keyboards first; PS/2 stays, so the machine is not lost |
| PS/2 coexistence (physical + emulated) | listen-before-talk (§7.3) |
| A PS/2 frame is starved past 2 ms | transmitter is top priority; frames are 660 µs |
| Companion absent or old firmware wedges the machine | fixed frames + ID probe + non-blocking 9K driver |
| Two bitstreams and flashes drift apart | register the protocol version in `0x00`; one `npm run` target per board |
| The 9K's `cs_n[2:0]` change breaks storage | land it alone, re-run the SPI sims, keep `cs_sel` 1/2 meaning intact |
| The emulator cannot see the companion | companion testbench + protocol model; the 9K's suite only ever sees the PS/2 wire or the injection port |
| Scope creep back into the 9K | the only permitted 9K change in this note is `cs_n[2]` |

## 15. Open questions

1. **1K or 4K?** It decides variant A vs B at the margin, and it is the only
   question that changes the architecture rather than a constant.
2. **Is MISO status needed**, or is the sound link write-only? Status lets a
   game sync a visual to the end of a crash; with a CS it is safe and ~10 LUT4.
3. **E0 extended keys — fix `ps2_rx` now?** Arrows and nav keys do not work on
   either path today. One decoder change, two new vector sets. Recommended
   before the effects library grows a menu that needs them.
4. **Auto-repeat in the companion** (PS/2-faithful, ~40 LUT4) — confirmed? The
   alternative, repeat in the 9K's decoder, changes behaviour for both sources.
5. **24 kHz or 15 kHz?** 24 kHz costs nothing and sounds better (§4.4).
6. **Which effects are mandatory?** If crash must be a *recorded* sample, the
   design needs the DMC-style channel and sample memory (~+120 LUT4, +1-2
   BSRAM) and the 1K is out.
7. **Four voices or three?** Three (two pulse + noise) is ~40 LUT4 smaller and
   still does effects; four gives the triangle bass a home.
8. **Does the game need per-event volume/pitch** (distance, size of the thing
   hit), or is a fixed preset per event enough?
9. **I2C — reserve now, and for what first?** RTC and OLED are the two that
   justify a master; otherwise the pins stay undocumented spares.
10. **Does the companion take power from the 9K's 3V3 header** or from its own
    USB? Check the 9K regulator's headroom and the current of the companion's
    LDO before wiring.
11. **Is the APU to be written portable to the 20K from the start** (no
    companion-specific assumptions in the register map, a wrappable top), or
    is it allowed to bake in the 12 MHz clock?
