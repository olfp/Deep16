# Hardware notes

## PS/2 keyboard attachment (implemented 2026-10-27)

The board build now has a receive-only PS/2 keyboard port:

- **RTL:** `rtl/ps2_rx.sv` — 2-FF synchronisers, 11-bit frame, odd parity,
  Set-2 make/break/extended decoding, Shift/Ctrl/Alt/Caps state.
- **Map:** `scripts/make_ps2map.mjs` writes `artifacts/image/ps2map.hex`, a
  2048 x 8 BSRAM pROM addressed by `{ctrl, caps, shift, scan_code}`. It is
  generated by `npm run image` and costs one of the free BSRAM blocks.
- **I2S pins:** **25 = BCLK, 26 = LRCLK, 27 = DIN** (J5 5/6/7), 3.3 V,
  driving a MAX98357A. Pin 25 is no longer the config-flash CS1; the P25Q32U
  moved to the MSPI pins 59–62.
- **Board pins:** **76 = PS/2 CLK, 77 = PS/2 DATA**, both 3.3 V bank 1 pins on
  the J6 header. They are the **3.3 V side** of the external level shifter.
- **Power/interface:** the keyboard still needs **5 V** and a mini-DIN-6
  socket/breakout. The GW1NR-9 is not 5 V tolerant (DS117 absolute maximum I/O
  voltage is 3.75 V), so the clock and data lines must go through a 5 V -> 3.3 V
  buffer such as two SN74LVC1G17s, a 74LVC245, or a level-shifter board. The
  FPGA only receives, so both channels point keyboard -> FPGA; on a board with
  DIR pins, set that direction.
- **Integration:** the decoded ASCII byte is pushed into both the UART RX FIFO
  (`0xF0042`, the D16nano console path) and the keyboard FIFO
  (`0xF0060`/`0xF0062`) with a one-cycle strobe. The D16nano BIOS, Forth and
  Flappy Bird therefore need **no software change**: Flappy already polls
  `0xF0066` bit 3 and pops `0xF0042`.
- **FIFO:** the keyboard FIFO is 16 entries (was 128). The PS/2 port is the only
  writer on the board; the shrunk FIFO keeps the architectural `0xF0060` port
  available without spending the old 128-word SSRAM.
- **Measured resource cost** (PS/2 slice alone, before timer/SPI/UART TX, 27 Oct
  2026): Logic 7,769 / 8,640, CLS 4,051 / 4,320, registers 2,747 / 6,771,
  BSRAM 17 / 26 (one block for `ps2map`), I/O 21 / 71. The PS/2 block is
  roughly +33 logic and +81 registers over the previous build; the FIFO shrink
  offsets part of that and leaves +16 CLS overall. The later timer/SPI/UART TX
  slice brings the tile build to 8,120 logic / 4,148 CLS; see below. On the
  older D16MINI UART/text build the PS/2 change lands at **4,305 / 4,320 CLS
  (15 free)**, so treat that build as full.
- **Tests:** `npm run sim:ps2` (pin-level receiver/map, no board) and
  `npm run sim:board` (the board build types a line through the PS/2 pins and
  checks the Forth echo). The hardware test waits for the level shifter.
- **Caveat:** PS/2 is not hot-plug. Connect the keyboard before power-up. Old
  keyboards can draw up to ~275 mA from 5 V; check the USB-C VBUS budget.

## Timer, SPI and UART TX (implemented 2026-10-27)

These are built only in the **D16nano tile/user-flash** build (`D16NANO` plus
`D16_PERIPH`); the older D16MINI text build is already at 4,305/4,320 CLS and
does not instantiate them. The packed-image tile experiment stays RX-only and
does not define `D16_PERIPH`.

- **Timer — `rtl/deep16_timer.sv`, `0xF0020`–`0xF002F`.** A 32-bit
  millisecond counter with a 32-bit compare and a sticky match flag. It is
  polled; the IRQ-enable bit is stored for a later SIC but no interrupt is
  wired into the CPU yet. Registers: CTRL `0x20`, VALUE low/high `0x22`/`0x24`,
  compare low/high `0x26`/`0x28`, STATUS `0x2A`.
- **SPI — `rtl/deep16_spi.sv`, `0xF0080`–`0xF008F`.** One byte-wide mode-0
  master, 8 bits MSB first, programmable half-period divider, two active-low
  chip selects. Registers: CTRL `0x80` (CS bits), STATUS `0x82` (busy, done,
  CS), DATA `0x84` (write starts, read returns the byte received), DIV `0x86`.
  SCK = CPU clock / (2 × (DIV+1)); DIV 0 is 3.375 MHz at 6.75 MHz, DIV 8 is
  ~375 kHz for SD initialisation. The SD protocol, flash commands and CRC live
  in software.
- **Pins.** SD socket: **36 SCK, 37 MOSI, 38 CS, 39 MISO**, 3.3 V. A separate
  external SPI flash can share SCK/MOSI/MISO and use **25** as its CS; the
  on-board configuration flash is deliberately **not** used. All are 3.3 V
  bank pins.
- **UART TX.** The D16nano UART now has a **one-byte TX holding register** (the
  64-byte RX FIFO stays). Status bit 1 (TX ready) and bit 3 (TX idle) are live;
  a write to `0xF0042` starts an 8N1 byte at the fixed baud divisor. This is the
  path for future X/YMODEM host transfers. The tile console still owns the
  screen; the UART TX is a second output, not a replacement.
- **Current tile build** (29 Oct 2026, after the timer IRQ + SIC): CLS
  **4,294 / 4,320 (26 free)**, LUT 6,577 + 761 ALU, FF 2,968, BSRAM 24 / 26;
  `dvi_pixel` **78.956 MHz**, `dvi_render` **30.937 MHz**, `psram_clk`
  **87.255 MHz**, `clk_cpu` 15.790, all clocks TNS 0 (`place_option 0`,
  `route_option 1`).
- **Measured cost** (tile/user-flash build, 28 Oct 2026, after PS/2, timer, SPI,
  UART TX, the three-bird sprite bank, the segmented map and the flash read
  port): Logic 8,283 / 8,640 (96 %), CLS **4,237 / 4,320** (**99 %, 83 free**),
  registers 2,985 / 6,771, BSRAM 23 / 26, I/O 26 / 71. The tile build closes
  `dvi_pixel` at 79.292 MHz (TNS 0) with place 0 / route 1.
- **Tests:** `npm run sim:timer`, `npm run sim:spi`, `npm run sim:uarttx`;
  `npm test` is the CPU suite. The 24K BSRAM builds (and `sim:board`) are
  retired - see `archive/24k-bsram/README.md`.
- **Not in this slice:** timer interrupt / SIC, an SD or flash protocol in
  hardware, and the external flash chip itself. The timer and SPI are polled.
  The SPI master is verified with a loopback; the SD protocol is now software,
  below.

## SD card driver (software, 2026-10-28)

The SD card needs no new RTL: `rtl/deep16_spi.sv` is a byte master and the
protocol is the **Forth driver in the boot script** (`forth/demo.fth`), so it
costs zero CLS and is testable in the JS core.

- **Registers and segment.** The SPI registers are ES-relative (ES = `0xF000`),
  so two kernel primitives were added for Forth: **`es@` ( off -- x )** and
  **`es!` ( x off -- )**. They are the only kernel change; everything else is
  boot-script Forth. `es@`/`es!` exist in both kernels (`forth.asm` and
  `forth_nano.asm`).
- **Identification** at **~100 kHz** (`sd-clk`, default 32 — one step below
  the 400 kHz the spec allows): 80 clocks with CS high, then CMD0, retried
  three times with a fresh 80-clock preamble because the first command after
  power-up is the one that fails on some cards; then CMD8 (with the `0x1AA`
  echo), the init poll, CMD58 (OCR, CCS → block vs byte addressing) and CMD16
  (512-byte blocks). Then the divider goes to 0 (3.375 MHz). Every command is
  framed by its own CS low→high edge. `sd-clk @` is the knob — `32 sd-clk !
  sd` re-runs it at another divider with no rebuild.
- **The init poll** tries the three ways a card can be brought out of idle:
  ACMD41 with HCS=1 (SDHC/SDXC), ACMD41 with HCS=0 (SDSC v1, which rejects the
  high-capacity bit), then CMD1 (MMC, which has no ACMD41). Each is bounded at
  1,024 tries and gives up as soon as the card stops answering, so a dead card
  reports in about a second instead of hanging.
- **Words** (all documented in `FORTH.md`): `sd` (report the card),
  `sd-init`, `sd-read ( sector -- n )`, `sd-write ( sector -- n )`, `sd-buf`,
  `blk`, `block ( sector -- addr )` (read on a miss), `save-block`.
  `sd-init` returns `0` when ready, otherwise the stage that failed:
  1 CMD0, 2 the CMD8 echo, 3 ACMD41, 4 CMD58, 5 the read token, 6 the write
  response. CMD8 is optional (a v1 card ignores it; CMD58's CCS picks block or
  byte addressing), every command gets its own CS edge, and `sd-r1 @` holds the
  raw byte the card sent in that stage, so `255` means nothing was on the bus.
- **Sector size and reach.** One 512-byte sector per call, held as **512
  characters, one per cell**, in a dictionary buffer (`sd-buf`, 512 words of
  `free`). Sector numbers are 16 bits: 32 MB of the card, which is also what a
  Forth block system asks for.
- **Image cost.** The boot script is now baked packed, **two characters per
  cell** (`embed_forth.mjs`, the assembler's `.string`), and `read_line`
  unpacks a line into `tib_kbd`; that halved the script's data-section cost and
  paid for the SD driver. Tile build after the SD driver: `dict_free 0x45E0`
  (1,056 words before the BIOS at `0x4A00`). Adding the flash `screen` code and
  its 2,048-cell unpack buffer moves it to `dict_free 0x471F`, so 737 words
  remain before the BIOS; the runtime dictionary reports `free` 32,578. The
  flat D16MINI builds are archived. Resources at that point:
  Logic 8,483 / 8,640, CLS **4,314 / 4,320**. The loader's read-back verify was
  then dropped and the flash read port added: 4,237 CLS, 8,283 logic.
- **Tests.** `tests/segmented.test.js` boots the segmented image in the JS core
  against a byte-level SD model (`SdCard` in `js/deep16_simulator.js`, wired to
  the SPI registers at `0xF0080`): identification, a sector written and read
  back, `block`'s cache and `save-block`, and a card that never answers (the
  driver reports `SD init error 1` instead of hanging). The model answers
  CMD0/8/55/41/58/16/17/24 and reports SDHC; the RTL master keeps its own
  loopback test (`npm run sim:spi`).
- **Source from the card.** `include ( first count -- )` reads `count` 512-byte
  sectors and hands them to `included`, so a source file is a run of sectors:
  lines separated by LF, the tail padded with LF. The starfield now lives on the
  card (`screens/starfield.fth`, seven sectors) instead of in the image; its
  load line is `1 7 include`. `scripts/make_screens.mjs` pads one or more `.fth`
  files into a sector-aligned blob, prints each file's `first count` and the
  `dd` line that writes it to the card. Up to 11 sectors (5.5 KiB) per include;
  the payload sits above a staging sector in `sd-buf`, so a read never
  overwrites a sector already moved into place. A load cannot be looped over:
  `included` ends the line it was called from, which is why one call takes the
  whole run.
- **Board test.** `npm run flash:tile`, then:

  ```text
  sd                  \ SD card ready
  0 sd-init . cr      \ 0
  sd-r1 @ . cr        \ 0
  ```
  If it reports a stage, `sd-r1 @ .` says what the card answered and
  `8 sd-clk ! sd` / `64 sd-clk ! sd` change the identification clock.
  ```text
  65 sd-buf c! 5 sd-buf 1+ c! 3 sd-write . cr    \ 0
  0 sd-buf c! 0 sd-buf 1+ c!
  3 sd-read . cr                                  \ 0
  sd-buf c@ . sd-buf 1+ c@ . cr                   \ 65 5
  ```
  `block`/`save-block` behave the same way; `blk` holds the sector in the
  buffer (`-1` before the first `block`).
- **Not yet:** more than one buffer, a FAT or file layer, `include` from the
  card, and 32-bit sector numbers.

## Segment-base split (`D16SEG`, second slice)

The tile/user-flash build enables the segmented map with `` `define D16SEG ``
in `d16tile_flash.sv`. The text and packed builds keep the old flat map.

- **Kernel code:** `CS=0`, code at `0x0100`; ILL/divtest code also in `CS=0`
  at `0x5000`/`0x5300`.
- **Kernel data + dictionary:** `DS=0x1000`.
  - `0x0000..0x1FFF` — SD block/sector buffers, still unused.
  - `0x2000..0x2FFF` — return stack, top `0x2FF0` down, 4,080 frames.
  - `0x3000..0x49F8` — kernel data and the boot script.
  - `0x4A00..0x57DC` — BIOS/demo data copy.
  - `0x5800..0xFFEF` — dictionary, about **42K words**.
- **Data stack:** `SS=0x2000`, top `0xFFF0`, 64K words. The BIOS and ILL
  handlers set their shadow `SS` to `0x2000` before using the caller's stack.
- **Return stack:** a DS offset window at `0x2FF0` down. It cannot be a segment
  of its own: every return-stack access is `LD`/`ST` through DS, so it has to
  stay a DS offset. It also has to stay *below* the dictionary (`0x5800`, grows
  up). The first segmented build kept it at `0x5FF0` with the dictionary
  starting at `0x5800`; that left only ~300 calls of headroom, so
  `1000 deep` overwrote the word it was running and froze the machine.
- **BIOS code:** `CS=0x3000`, copied by the loader from the flat image's
  `0x4A00..0x57FF` to `0x30000..0x30DFF`; SWI target `0x3000:0`. BIOS/demo
  data is in `DS=0x1000`; the D16D demo still uses the flat segment-0 data
  copy at `DS=0x04A0`, and the BIOS f6 restores `DS=0x1000` on return.
- **Vectors:** SWI/ILL vectors are written through `CS=0` to physical 0/2;
  they cannot use the new DS.
- **Loader:** `flash_boot` writes the flat image, the `DS=0x1000` data copy,
  and the `0x3000` BIOS/demo copy. The CRC covers the flash read; the read-back
  verify was dropped; the CPU read port it paid for was removed again in
  phase 2a. The extra logic is gated by `D16SEG`; the text build's loader is
  unchanged.
- **Measured tile build (28 Oct phase-1 image):** Logic 8,283 / 8,640
  (96 %), CLS 4,237 / 4,320 (99 %, 83 free), registers 2,985 / 6,771,
  BSRAM 23 / 26, I/O 26 / 71. The config-flash bridge adds the mux/pins:
  4,274 / 46 free in the flashed phase-1 build. Phase 2a (code only) is
  4,259 / 61 free but its dvi_pixel placement is 65.973 MHz; it is not flashed.
- **Simulation:** `tests/segmented.test.js` scatters the image the way
  `flash_boot` does and boots it in the JS core: banner, `free`, arithmetic,
  1,000-deep recursion, `catch`/`throw`, and 20,000 cells on the data stack.
  It is the only coverage of this map without the board.
- **Hardware status:** the previous slice (data/dictionary segment) booted on
  the board, ran Flappy, `1 2 + .`, `ver` and the UART, and reported `free`
  41,260 — but `1000 deep` froze, which is the return-stack/dictionary
  collision above. The return-stack move is source-only and needs the next
  board test.
  `flash:tile` must regenerate the user image with `D16SEG=1`; it now does.
  If `free` still reports 39,212, the old flat user image is still in the
  on-die flash even though the segmented bitstream is loaded.
- **Done:** the SD driver/block layer, `include`, and the config-flash SPI
  bring-up (JEDEC ID, BP=2 MB, sector program/read). The on-die flash CPU read
  port (`flash@`/`screen`) was removed in phase 2a; the 4 KB slice layer moves
  to the config flash next (`ADVARCH.md`).

## USB keyboard attachment (alternative)

For attaching a USB keyboard to the Tang Nano 9K without a separate
microcontroller, consider the **usb_hid_host** FPGA core:

- Repo: https://github.com/nand2mario/usb_hid_host
- Compact USB HID host core supporting **keyboards, mice, and gamepads**.
- **No CPU required** — all-in-one design; reports keystrokes directly.
- Small footprint: **< 300 LUTs, < 250 registers, 1 BRAM block** — fits the
  Tang Nano 9K budget (and is much lighter than a Pi Pico / external MCU).
- Vendor-agnostic Verilog; includes a Tang Nano 9K/20K sample project.
- Also has a companion **usb_host_pmod** board for pmod-style connections.

Integration: add `usb_hid_host.v`, `usb_hid_host_rom.v`, and
`usb_hid_host_rom.hex` to the build, wire the USB data lines to a free
header/pmod, and feed the reported key codes into the existing keyboard
FIFO (`0xF0060`/`0xF0062`) — keeping the ASCII/scan-code contract the
BIOS and Forth kernel already expect.

This is the preferred lightweight alternative to an external USB-host MCU
(Pi Pico, STM32, etc.) for the standalone DVI + keyboard build.
