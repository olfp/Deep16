# Build, Test and Image Pipeline

Everything is driven from `package.json`; there is no bundler, no Makefile at the
root, and no hidden build step. The `scripts/` directory holds Node generators
and Bash wrappers, and each one is invoked by a named npm script.

The first rule of this repository is worth stating before the details:

- **`wasm/pkg/` and `rtl/pkg/` are committed on purpose.** The IDE and the tests
  load them directly.
- **`artifacts/` is not committed.** It is gitignored, because it holds generated
  images and screenshots.
- Changing a source without re-running its generator leaves the old artifact in
  place, and the failure is silent.

## Committed versus generated

| Path | State | Regenerated by |
|---|---|---|
| `wasm/pkg/` | Committed | `npm run build:wasm` |
| `rtl/pkg/` | Committed | `npm run build:rtl:wasm` |
| `rtl/dvi/font8x15.hex` | Committed font ROM | `node scripts/bdf_to_font.mjs <font.bdf>` |
| `artifacts/image/*` | Gitignored | `npm run image` (or `synth:tile`) |
| `fpga/gowin/impl/` | Gitignored build output | `npm run synth:tile` |

If you change anything under `rtl/`, re-run `npm run build:rtl:wasm`. The tests
will happily exercise the previous model otherwise — that is exactly the failure
mode the committed package creates.

## Script map

### Build and lint

| Script | What it does |
|---|---|
| `build:wasm` | `wasm-pack build --target web` into `wasm/pkg/` |
| `build:rtl:wasm` | Verilator + Emscripten → `rtl/pkg/deep16_rtl_gen.{js,wasm}`, plus the hand-written `deep16_rtl.js` glue |
| `build:rtl` | Native Verilator binary `obj_dir/deep16_rtl` for differential debugging |
| `lint:rtl`, `lint:mini`, `lint:board` | `verilator --lint-only -Wall` over the core, the D16MINI build and the board wrapper |
| `serve` | Static HTTP server for the IDE |
| `ui:shot` | Puppeteer screenshot of the IDE |

`build:rtl:wasm` verilates `deep16_top` and compiles the harness with `em++`,
exporting the same C-style API the wasm-bindgen core exposes. That shared shape
is why the IDE can switch cores by name alone.

### Image generation

| Script | Output |
|---|---|
| `image` | `node scripts/make_image.mjs` — the whole image set |
| `assets:gfx` | Generated tile/sprite/palette graphics blob |
| `render:tile` | Deterministic headless PNG frames |
| `installer:tile` | D16D image plus the installer bitstream path |

`make_image.mjs` assembles `forth.asm` or `forth_nano.asm`, lays it into the
24K-word window with `0xFFFF` fill, and writes:

| File | Purpose |
|---|---|
| `image.hex`, `image.mi` | Memory initialisation for simulation and Gowin |
| `image-packed.hex` | Range-packed image for the non-D16D BSRAM build |
| `image.flash.hex`, `image.flash.bin` | Installer words and the 608 Kbit config-flash boot image |
| `image.manifest.json` | Sizes, addresses, build id |
| `font8x15.hex`, `tilefont.hex`, `birdsprite.hex`, `ps2map.hex` | Font, tile bank, sprite bank, PS/2 map |

It also enforces the image invariants: words outside the window are dropped and
reported, the BIOS address and dictionary free count are printed, and the packed
form is checked against the flat image when it is built. The tile build sets
`D16NANO=1 D16D=1 D16SEG=1` and deliberately does **not** write a packed image,
because the D16D kernel is larger than the 16-block budget.

The D16D image no longer bakes Pac-Man: the kernel grew to `0x434D`, so the game
is assembled by `buildPacman()` into a 1,695-word block, wrapped by
`make_slices.mjs` as a type-4 slice (slice 10 at `0x20A000`) and loaded into
segment `0x2000` by `games.fth` at run time. `BAKE_PACMAN=1` (Node) or
`bakePacman: true` (browser builder) puts it back at `0x4330` for a preview;
the headless renderer uses that path.

### Boot-script embedding

`scripts/embed_forth.mjs` rewrites the block between the generated markers in
`asm/forth.asm` and `asm/forth_nano.asm` from `forth/demo.fth`. It packs two
characters per cell and enforces a 120-character line limit.

```sh
node scripts/embed_forth.mjs           # rewrite
node scripts/embed_forth.mjs --check   # exit 1 if stale
```

`tests/boot-script.test.js` runs the `--check` path, so a stale baked script
fails the suite instead of shipping.

### Asset generators

| Script | Produces |
|---|---|
| `bdf_to_font.mjs` | 8 × 15 BDF → the DVI font ROM |
| `make_tile_font.mjs` | Regular and italic 4bpp text pages for the tile bank |
| `make_bird_sprite.mjs` | Bird/cloud sprite bank |
| `make_art.mjs` | Quantised 4bpp art tiles from `assets/art` |
| `make_ps2map.mjs` | 2048 × 8 Set-2 → ASCII table |
| `make_slices.mjs` | 4 KB slice image: source screens plus the type-4 Pac-Man block |
| `make_screens.mjs` | Forth source → SD-card or flash screen images |
| `make_pacman_art.mjs` | Pac-Man maze/tables, dot/wall/ghost tiles and sprite frames |
| `make_flash_assets.mjs` | Packs font/tile/sprite/palette data into `js/deep16_flash_assets.js` |
| `make_showcase.mjs` | The D16D menu+Flappy block and `buildPacman()` |
| `render_tile.mjs` | Headless menu/Flappy/Pac-Man/console renderer |

`make_image.mjs` calls the font, sprite and PS/2 generators itself, so the
console font, tile font and keyboard map cannot drift from each other.

### Graphics and renderer

`assets:gfx` runs `make_tile_font.mjs` + `make_bird_sprite.mjs` +
`make_flash_assets.mjs` (the latter also packs the palette and the Pac-Man art).
`render:tile` builds the D16D image in memory, optionally bakes Pac-Man at
`0x4330`, loads the same graphics blob through `deep16_gfx_loader.js`, runs a
fixed 0x1000-step frame clock and writes PNGs. The scenes are `menu`, `flappy`,
`pacman` and `console`; `--key=BYTE` holds a UART byte until the game consumes
it.

### Verilator device simulations

Each peripheral has a small testbench and a `sim:*` script:

| Script | Module |
|---|---|
| `sim:ps2`, `sim:timer`, `sim:spi`, `sim:uarttx` | PS/2 receiver, timer, SPI, UART TX |
| `sim:i2s`, `sim:sic`, `sim:irq` | I2S, interrupt controller, `core3` IRQ entry |
| `sim:dvi`, `sim:dvi:tile` | Text and tile DVI paths |
| `sim:bootspi`, `sim:flashboot` | Config-flash read and boot loader |
| `sim:installer` | On-die flash installer |
| `test:uart` | UART FIFO testbench |

They follow one pattern: `verilator --cc --exe --build` into an `obj_*`
directory, then run the binary.

### Synthesis and flashing

| Script | Action |
|---|---|
| `synth:tile` | Regenerates the D16D image, then runs Gowin synthesis and P&R |
| `flash:tile` | Writes bitstream, boot image and slices with `openFPGALoader` |
| `flash:slices` | Writes only the source slices |
| `synth:installer`, `installer:tile` | Installer bitstream paths |

`synth:tile` runs `scripts/build_gowin_tile_flash.sh`, which expects Gowin EDA
at `GOWIN_APP` (macOS path by default), regenerates the image with
`D16NANO=1 D16D=1 D16SEG=1`, and drives `gw_sh` with
`fpga/gowin/build_tile_flash.tcl`.

`flash:tile` is the only supported board path. It regenerates the same image,
writes the bitstream with `openFPGALoader -f`, writes the boot image at
`0x100000`, verifies it by read-back, and writes the slices at `0x200000` last.
The flash toolchain is not part of the repository; without `gw_sh` or
`openFPGALoader` these scripts fail early rather than producing a partial image.

## Diagnostics

| Command | Purpose |
|---|---|
| `sweep:rtl` | Execute all 65,536 instruction words from four seeds on JS and RTL; must report 0 divergences |
| `trace:rtl -- asm/forth.asm 200 --keys "1 2 + .\n"` | Instruction trace side by side with the JS core |
| `node scripts/bench.mjs` | MIPS of all three cores |
| `rtl_smoke.mjs` | Small native RTL smoke run |
| `js_fib_test.js`, `js_forth_test.js`, `wasm_fib_test.js`, `assembler_case_test.js` | Standalone legacy probes |

The sweep is deliberately outside `npm test`: it is a slow, high-volume check,
not a regression test. The fuzz test in the suite covers sequences; the sweep
covers words no real program executes.

## The test suite

`npm test` is `node --test tests/*.test.js` — currently about 40 files, minutes
on one core. The suite includes the FiT engine/store-hook/clock tests, the D16D
image and UI tests, the Pac-Man block/game tests, the headless renderer and the
type-4 slice tests, in addition to the CPU/Forth/console suite. `tests/helpers.js` is the shared harness:

- loads the browser scripts with `vm.runInThisContext` and reads the classes
  back by name;
- `assemble`, `optimize`, `buildMemory`, `readScreen`;
- `runJs`, `runWasm`, `runRtl`, all returning the same result shape, so a test
  can compare cores field by field;
- loads the committed WASM and RTL packages without a build.

The files fall into groups:

| Group | Files |
|---|---|
| Toolchain | `assembler`, `disassembler`, `optimizer`, `mov-imm2` |
| Graphics | `tile-engine`, `tile-store-hook`, `tile-clock`, `flash-assets`, `showcase-render` |
| Games | `pacman`, `showcase-art`, `showcase-death`, `d16d-image`, `ui-d16d`, `slices-binary` |
| Cores | `cores`, `flags`, `shadow`, `wasm-state`, `smv-write` |
| RTL | `rtl`, `rtl-uart`, `fuzz`, `ill-trap`, `segmented`, `nano-*` |
| Software | `forth`, `boot-script`, `uart`, `uart-kernel`, `terminal`, `image`, `examples` |
| Hardware/console | `console-parity`, `tile-console`, `ps2map`, `font`, `scroll4` |
| IDE | `ui-core`, `ui-stats`, `ui-terminal` |
| Showcase | `showcase-art`, `showcase-boot`, `showcase-death`, `showcase-weights` |

`tests/examples.test.js` is not a directory dump: it runs the eight shipped
examples and excludes an explicit `LEGACY` set (`bios_test.asm`,
`deep16_rom.asm`, `deep16bios.asm`, `test_suite.asm`). Those four are
interactive, need assembler directives the JS assembler does not implement, or
are generated in old syntax. The root build/debug scripts and their sources are
tracked; their scratch output (`deep16_rom.bin`, `test_output*.txt`,
`debug_log.txt`, `debug_trace.txt`, `screen_dump.txt`, `trace_*.txt`) is
gitignored.

Two tests carry most of the verification weight: `rtl.test.js` (three-way parity,
decode sweep hooks and pipeline behaviour) and `fuzz.test.js` (random programs
compared after every step). The fuzz test asserts that at least one program
entered the shadow bank and at least one took a non-sequential path, and prints
the real counts; that is weaker than the "49 of 60" figure the README quotes, so
treat the printed coverage line as the measurement. The fuzz depth is
configurable:

```sh
FUZZ_SEEDS=500 FUZZ_STEPS=1000 npm test
```

## Rebuild matrix

| Change | Re-run |
|---|---|
| `wasm/deep16-wasm/src/lib.rs` | `npm run build:wasm` |
| Anything under `rtl/` | `npm run build:rtl:wasm` (and `npm run lint:rtl`) |
| `forth/demo.fth` | `node scripts/embed_forth.mjs` |
| `asm/forth.asm`, `asm/forth_nano.asm` | `npm run image` (and `npm test`) |
| Font BDF | `node scripts/bdf_to_font.mjs <font.bdf>` |
| Art or tile assets | the relevant `make_*` generator, then `npm run image` |
| Board build (RTL or kernel change) | `npm run synth:tile`, then `npm run flash:tile`; the `.fs` must be newer than the RTL, or the board silently runs the old logic |
